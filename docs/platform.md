# Розгортання та вибір платформи цифрового двійника

**Об'єкт дослідження:** автоматична кавомашина (цифровий двійник `cm-001`).  
**Лабораторна робота:** № 2, заняття 1.  
**Предмет:** «Архітектури імерсивних систем та платформ цифрових двійників».

## Мета

Розгорнути локальну платформу цифрового двійника, перевірити доступність її HTTP API, визначити структуру двійника кавомашини та обґрунтувати вибір платформи шляхом порівняння з альтернативними рішеннями.

## Розгортання платформи

Для експериментального стенда обрано Eclipse Ditto 3.9.7. Середовище розгорнуто за допомогою Docker Compose 2.34.0 і Docker 28.0.4 у Windows. Конфігурації розміщено в каталозі `platform/`, а вихідні файли Ditto версії 3.9.7 локально завантажено до `platform/ditto/`. Цей каталог виключено з Git.

До складу стенда входять:

| Компонент | Призначення | Локальний доступ |
|---|---|---|
| Eclipse Ditto (Things, Policies, Things-Search, Gateway, Connectivity) | Збереження стану двійника, контроль доступу, пошук та інтеграція | `http://localhost:8080` |
| MongoDB | Сховище даних платформи Ditto | Лише у внутрішній мережі Docker |
| Eclipse Mosquitto | MQTT-брокер для телеметрії | `127.0.0.1:1883` |
| InfluxDB OSS 2.9 | Історія сигналів і затримок синхронізації | `http://localhost:8086` |
| Grafana OSS 13 | Візуалізація історії та результатів вимірювання | `http://localhost:3000` |
| nginx (`web`) | Публікація моделей, вебподання та проксі для API читання | `http://localhost:8090` |

Додатково до складу розгортання Ditto входять nginx, Swagger UI та вебінтерфейс Ditto. За командою `docker compose ps` підтверджено запуск **13 контейнерів**. Сервіси `policies`, `things`, `things-search`, `connectivity` і `gateway` мають стан `healthy`.

Перевірка конфігурації та запуск:

```powershell
cd platform
docker compose config --quiet
docker compose up -d
docker compose ps
curl.exe http://localhost:8080/health
```

Результат перевірки стану платформи:

```json
{"status":"UP"}
```

Отже, локальний стенд успішно розгорнуто, а шлюз Ditto відповідає на HTTP-запити. Попередження Docker Compose про застарілий атрибут `version` у файлі Ditto не перешкоджає роботі. Перевірка наскрізного передавання MQTT-телеметрії до двійника виконується на занятті 3 і **не входить** до результатів поточного етапу.

Відповідно до ISO 23247, емулятор кавомашини відноситься до домену спостережуваного об'єкта (OME), Mosquitto та відображення повідомлень — до домену зв'язку з пристроями (DCE), Ditto й InfluxDB — до домену цифрового двійника (DTE), а вебподання та Grafana — до домену користувача (UE).

## Перевірка API

Для перевірки REST API створено тестовий двійник з ідентифікатором `org.pzks:test-1`. Відправлено `PUT`-запит до `/api/2/things/org.pzks:test-1` з JSON-тілом:

```json
{
  "attributes": {
    "purpose": "API connectivity test"
  }
}
```

Під час виконаної перевірки сервер повернув **HTTP 204 No Content**, що підтверджує успішне застосування запиту. Код `201 Created` можливий під час першого створення, тоді як `204` відповідає успішному оновленню чи повторному запису ресурсу.

Запит `GET /api/2/things/org.pzks:test-1` повернув:

```json
{
  "thingId": "org.pzks:test-1",
  "policyId": "org.pzks:test-1",
  "attributes": {
    "purpose": "API connectivity test"
  }
}
```

Запит `GET /api/2/policies/org.pzks:test-1` підтвердив наявність автоматично створеної політики `DEFAULT`. Суб'єкт `nginx:ditto` отримав права `READ` та `WRITE` для ресурсів `thing:/`, `policy:/` і `message:/`; списки `revoke` порожні.

Таким чином, перевірено можливість запису й читання даних двійника та застосування політики доступу. Тестовий об'єкт `org.pzks:test-1` призначений лише для перевірки API й не є основним двійником кавомашини.

## Структура двійника

Для кавомашини передбачено окремий примірник `org.pzks:cm-001`. Структуру визначено на основі восьми сигналів із реєстру ЛР1. Паспортні характеристики розміщуються в `attributes`, поточні параметри — у `features`, функції задаються повідомленнями `inbox`, а зв'язки з іншими об'єктами — атрибутами з ідентифікаторами відповідних двійників.

| Елемент | Вид | Відповідник у Ditto | Джерело |
|---|---|---|---|
| Виробник | Паспортна властивість | `attributes/manufacturer` | Паспорт обладнання |
| Серійний номер | Паспортна властивість | `attributes/serialNo` | Паспорт обладнання |
| Модель кавомашини | Паспортна властивість | `attributes/modelName` | Паспорт обладнання |
| Температура бойлера | Стан | `features/thermal/properties/temperature` | Сигнал `Temperature` з ЛР1 |
| Потужність нагрівача | Стан | `features/thermal/properties/heaterPower` | Сигнал `HeaterPower` з ЛР1 |
| Тиск води | Стан | `features/hydraulics/properties/pressure` | Сигнал `Pressure` з ЛР1 |
| Витрата води | Стан | `features/hydraulics/properties/flowRate` | Сигнал `FlowRate` з ЛР1 |
| Рівень води | Стан | `features/hydraulics/properties/waterLevel` | Сигнал `WaterLevel` з ЛР1 |
| СКЗ вібрації помпи | Стан | `features/hydraulics/properties/pumpVibrationRms` | Сигнал `PumpVibrationRms` з ЛР1 |
| Активність приготування | Стан | `features/operation/properties/brewingActive` | Сигнал `BrewingActive` з ЛР1 |
| Наявність резервуара | Стан | `features/operation/properties/waterTankPresent` | Сигнал `WaterTankPresent` з ЛР1 |
| Почати приготування | Функція | `messages/inbox/start-brewing` | Команда оператора / сценарій керування |
| Зупинити приготування | Функція | `messages/inbox/stop-brewing` | Команда оператора / сценарій керування |
| Резервуар для води | Зв'язок `hasPart` | `attributes/waterTankThingId` | Структура кавомашини; посилання на окремий двійник резервуара |

Відповідні функціональні блоки:

- `thermal` — температурний стан і потужність нагрівача;
- `hydraulics` — тиск, витрата води, рівень води та вібрація помпи;
- `operation` — активність приготування й наявність резервуара;
- `sync` — службові поля `seq` (порядковий номер повідомлення) і `ts` (час відліку на джерелі), потрібні для подальшої перевірки синхронізації.

Зв'язок `hasPart` означає, що резервуар є складовою частиною кавомашини. Ditto не зберігає такий зв'язок як окрему графову сутність: у примірнику кавомашини планується зберігати `thingId` резервуара, а семантику відношення визначити в онтології `twin/ontology.ttl` (заняття 2). Наявність резервуара як окремого двійника на цьому етапі не перевірялася.

Команди `start-brewing` і `stop-brewing` наведено як **проєктовані функції** інформаційної моделі: їхню фактичну обробку та зворотний канал керування ще не реалізовано. Поточний тестовий двійник містить лише атрибут `purpose`; створення повного примірника `cm-001` із Thing Model заплановано на заняття 2.

## Порівняння платформ

Порівняно три платформи: **Eclipse Ditto**, **Azure Digital Twins** та **AWS IoT TwinMaker**. Для лабораторного стенда пріоритетними є можливість локального розгортання, відкритість технологій і невисока вартість експериментів. Ваги критеріїв визначено до виставлення оцінок. Оцінювання виконується за шкалою від 1 (найменша відповідність) до 5 (найбільша відповідність).

| Критерій | Вага | Eclipse Ditto | Azure Digital Twins | AWS IoT TwinMaker |
|---|---:|---:|---:|---:|
| Відкритість технологій та форматів | 0,25 | 5 | 3 | 2 |
| Вартість володіння для навчального стенда | 0,20 | 4 | 3 | 3 |
| Можливість локального розгортання | 0,20 | 5 | 1 | 1 |
| Масштабованість | 0,15 | 4 | 5 | 4 |
| Підтримка протоколів та інтеграцій | 0,10 | 5 | 3 | 3 |
| Зрілість екосистеми та документації | 0,10 | 4 | 5 | 4 |
| **Зважена оцінка S** | **1,00** | **4,55** | **3,10** | **2,60** |

Підсумкова оцінка обчислюється за формулою:

$$
S = \frac{\sum_i w_i s_i}{\sum_i w_i}
$$

де $w_i$ — вага критерію, $s_i$ — оцінка платформи за цим критерієм. Оскільки сума ваг дорівнює одиниці, для Eclipse Ditto:

$$
S_{Ditto} = 0{,}25\cdot5 + 0{,}20\cdot4 + 0{,}20\cdot5 + 0{,}15\cdot4 + 0{,}10\cdot5 + 0{,}10\cdot4 = 4{,}55
$$

### Обґрунтування оцінок

1. **Відкритість.** Eclipse Ditto є відкритим програмним забезпеченням і надає API та модель інтеграції для цифрових двійників [1, 2]. Azure Digital Twins використовує документований формат DTDL, але сама платформа є керованим хмарним сервісом [4, 5]. AWS IoT TwinMaker також є керованим сервісом, його модель компонентів та конекторів тісно пов'язана з інфраструктурою AWS [7]. Тому оцінки становлять відповідно 5, 3 і 2.
2. **Вартість володіння.** Ditto можна запускати без плати за ліцензію, але ресурси хоста й супровід контейнерів мають власну вартість (4). Azure тарифікується за операціями, повідомленнями й одиницями запитів (3) [6]. AWS пропонує декілька тарифних моделей, а для підключених сховищ і додаткових сервісів можливі окремі витрати (3) [8].
3. **Локальне розгортання.** Ditto розгортається локально через Docker Compose (5) [1]. Azure Digital Twins і AWS IoT TwinMaker представлені як керовані хмарні сервіси, а не як готові дистрибутиви для локального встановлення (по 1) [4, 7].
4. **Масштабованість.** Ditto побудовано з кількох мікросервісів, об'єднаних у кластер, що підтримує розподілення навантаження, проте для цього потрібне адміністрування (4) [2]. Azure позиціонується як масштабована PaaS-платформа (5) [4]. TwinMaker також підтримує велику кількість сутностей, але має документовані квоти й обмеження частоти API (4) [9].
5. **Протоколи та інтеграції.** Ditto безпосередньо підтримує зв'язки через MQTT, HTTP, AMQP та Kafka і відображення payload (5) [3]. Azure отримує IoT-дані через IoT Hub та інші сервіси Azure (3) [4]. TwinMaker інтегрується із джерелами даних через готові та користувацькі конектори, зокрема AWS Lambda (3) [7].
6. **Зрілість екосистеми.** Ditto має документацію та відкритий проєкт Eclipse Foundation (4) [1, 2]. Azure має розвинену документацію, SDK, інструменти й інтеграції з іншими сервісами Microsoft (5) [4, 5]. AWS TwinMaker має офіційну документацію й інтеграцію з екосистемою AWS, але для частини джерел необхідно створювати власні конектори (4) [7].

Ці бали є **експертною порівняльною оцінкою придатності до даної лабораторної роботи**, а не результатом незалежних тестів продуктивності чи універсальним рейтингом платформ.

### Прийняте рішення

За підсумками оцінювання обрано **Eclipse Ditto (4,55 бала)**. Платформа забезпечує локальне розгортання, підтримує необхідний MQTT-канал, відокремлює стан цифрового двійника від формату телеметрії та не вимагає платної хмарної підписки для навчальних експериментів. Основні компроміси — потреба в локальних ресурсах, налаштуваннях сервісів і самостійному супроводі стенда.

Архітектурне рішення буде зафіксовано в `docs/adr/0004-vybir-platformy.md`.

## Висновок

У межах першого заняття розгорнуто 13 контейнерів платформи цифрового двійника. Перевірка `/health` повернула `UP`, REST API дозволив записати й отримати тестовий двійник, а політика підтвердила права читання та запису. Для кавомашини визначено майбутні атрибути, функціональні блоки, функції та зв'язок із резервуаром. За результатами зваженого порівняння обрано Eclipse Ditto; реалізація інформаційної моделі, каналу телеметрії та вимірювання затримок заплановані на наступні заняття.
