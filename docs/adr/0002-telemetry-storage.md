# ADR-0002. Сховище часових рядів для телеметрії

## Статус

Прийнято, 2026-10-19.

## Контекст

Реєстр містить вісім сигналів із різними частотами
опитування.

Розрахований обсяг самих значень телеметрії:

приблизно 22.3 МБ на добу.

Обсяг за рік без урахування службових полів:

22.3 × 365 ≈ 8.1 ГБ.

Фактичний обсяг буде більшим через часові мітки,
ідентифікатори, metadata та індекси.

Основними запитами до історичних даних є:

- значення сигналу за часовий інтервал;
- агрегати за період;
- аналіз тенденцій;
- пошук даних навколо аномалії.

## Варіанти

### 1. Звичайна реляційна база даних

Переваги:

- проста розробка;
- знайомий SQL;
- підтримка транзакцій.

Недоліки:

- необхідно самостійно організовувати ефективну
  роботу з великими часовими рядами;
- агрегація і retention потребують додаткової логіки.

### 2. Time-Series Database

Переваги:

- оптимізована для часових даних;
- ефективні запити за інтервалами;
- агрегація;
- retention policies;
- можливість downsampling.

Недоліки:

- ще одна спеціалізована технологія;
- додаткове адміністрування.

### 3. Файловий журнал

Переваги:

- мінімальна складність;
- низька вартість реалізації.

Недоліки:

- незручний пошук;
- складна агрегація;
- погано масштабується для аналітики.

## Рішення

Для архітектури платформи обрано сховище,
орієнтоване на часові ряди.

Логічний компонент називається:

Telemetry Repository.

Конкретна СУБД може бути обрана під час реалізації.

Передбачається політика:

- актуальні дані зберігаються з повною роздільністю;
- старі дані можуть агрегуватися;
- архівна гілка не блокує оновлення поточного стану
  цифрового двійника.

## Наслідки

Позитивні:

- ефективна робота з історичною телеметрією;
- природні запити за часовими інтервалами;
- простіша побудова графіків та аналітики;
- можливість retention і downsampling.

Негативні:

- потрібно підтримувати окреме сховище;
- необхідно визначити політику зберігання;
- можлива втрата деталізації після агрегації старих даних.
