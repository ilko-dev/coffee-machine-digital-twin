# ADR-0001. MQTT як транспорт телеметрії

## Статус

Прийнято, 2026-10-19.

## Контекст

Платформа повинна регулярно передавати телеметрію восьми
сигналів автоматичної кавомашини.

Найшвидші сигнали передаються з частотою 10 Гц.
Платформа також повинна підтримувати двобічний зв'язок,
контроль доставки та слабку зв'язаність джерела і споживачів.

Розглядалися MQTT, HTTP та OPC UA.

Наукова робота Cho та Noh (2024) демонструє використання
MQTT для синхронізації фізичного виробничого обладнання
та цифрового двійника в реальному часі.

Джерело:
Cho Y., Noh S. D.
Design and Implementation of Digital Twin Factory
Synchronized in Real-Time Using MQTT.
Machines, 2024, 12(11), 759.
DOI: 10.3390/machines12110759.

## Варіанти

### 1. HTTP REST

Переваги:

- простий;
- широко підтримується;
- зручний для request/response API.

Недоліки:

- джерело повинно знати адресу одержувача;
- не є природною pub/sub моделлю;
- менш зручний для постійного потоку телеметрії.

### 2. MQTT

Переваги:

- модель publish/subscribe;
- слабка зв'язаність компонентів;
- підтримка QoS;
- Last Will;
- retained messages;
- невеликі накладні витрати;
- природно підходить для IoT-телеметрії.

Недоліки:

- потрібен окремий MQTT Broker;
- потрібно керувати topics і ACL.

### 3. OPC UA

Переваги:

- багата інформаційна модель;
- промислова стандартизація;
- вбудовані засоби безпеки.

Недоліки:

- складніша реалізація;
- надлишкова функціональність для невеликого
  навчального об'єкта.

## Рішення

Для передачі оперативної телеметрії обрано MQTT.

Eclipse Mosquitto використовується як MQTT Broker.

Структура topics:

coffee-machine/{machineId}/sensor/{sensorId}

Для стану пристрою:

coffee-machine/{machineId}/status

Для команд передбачається:

coffee-machine/{machineId}/command/{commandName}

REST API залишається для клієнтських запитів,
але не використовується як основний транспорт телеметрії.

## Наслідки

Позитивні:

- Publisher і Consumer не залежать безпосередньо один від одного;
- можна підключати декілька споживачів;
- доступні QoS і Last Will;
- архітектура легко масштабується.

Негативні:

- з'являється окремий інфраструктурний компонент MQTT Broker;
- необхідно адмініструвати topics, доступ і стан Broker;
- при недоступності Broker потрібна логіка reconnect.
