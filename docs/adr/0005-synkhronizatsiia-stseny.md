# ADR 0005. Синхронізація спільного стану 3D-сцени

## Контекст

3D-сцена цифрового двійника використовується одночасно кількома учасниками.

Необхідно синхронізувати:

- позиції та орієнтації учасників;
- спільні позначки;
- зміни віртуального стану сцени.

При цьому фізичний стан кавомашини вже зберігається в Eclipse Ditto та надходить клієнтам через REST і SSE.

Передавання цього самого стану через окремий сервер сеансу створило б два незалежні джерела істини для одного набору даних.

Також необхідно забезпечити прийнятну поведінку віддалених аватарів за різних мережевих затримок.

## Варіанти

### 1. Повна синхронізація через Eclipse Ditto

Позиції учасників і позначки можна було б представити як частину Thing-моделі та передавати через Ditto.

Переваги:

- одна технологія обміну;
- відсутність окремого сервера сеансу.

Недоліки:

- змішування фізичного стану цифрового двійника з тимчасовим станом інтерфейсу;
- надлишкове навантаження на платформу цифрових двійників;
- складніша обробка високочастотних оновлень позицій.

### 2. Peer-to-peer синхронізація між браузерами

Клієнти могли б обмінюватися станом без центрального сервера.

Переваги:

- відсутність центрального сервера передачі стану;
- потенційно менша затримка між двома учасниками.

Недоліки:

- складніше забезпечити однаковий стан позначок;
- складніше визначити джерело істини;
- ускладнюється підключення більшої кількості користувачів;
- зростає складність мережевої взаємодії.

### 3. Авторитетний сервер сеансу через WebSocket

Окремий Node.js сервер зберігає спільний віртуальний стан і розсилає snapshot клієнтам.

Фізичний стан цифрового двійника сервер сеансу не дублює.

Переваги:

- чітке розділення відповідальності;
- сервер є єдиним джерелом істини для спільних позначок;
- проста підтримка кількох учасників;
- можливість централізованої перевірки повідомлень;
- можливість моделювати мережеві профілі;
- природна підтримка snapshot, interpolation та extrapolation.

Недоліки:

- сервер є додатковим компонентом системи;
- сервер створює додаткову точку відмови;
- зі збільшенням кількості учасників збільшується мережевий потік.

## Рішення

Обрано авторитетний сервер сеансу на Node.js із WebSocket.

Розподіл джерел істини:

- Eclipse Ditto відповідає за фізичний стан цифрового двійника;
- сервер сеансу відповідає за спільний віртуальний стан.

Клієнти надсилають свої пози та орієнтації з частотою приблизно 20 Гц.

Сервер формує snapshot спільного стану кожні:

```text
50 мс
```

Спільні позначки зберігаються сервером. Створення та видалення позначок проходить через нього.

Для відображення віддалених учасників основним режимом обрано інтерполяцію між snapshot.

Для експериментального порівняння також реалізовано екстраполяцію не більше ніж на 250 мс.

Результати вимірювань показали, що інтерполяція має більшу затримку, але практично не створює просторової похибки.

Екстраполяція зменшує затримку, але за мобільного профілю може призводити до значного відхилення положення.

Тому основним режимом синхронізації спільної сцени є інтерполяція.

## Наслідки

Позитивні наслідки:

- фізичний і віртуальний стани мають окремі джерела істини;
- клієнти не дублюють стан Ditto через сервер сеансу;
- спільні позначки мають узгоджений серверний стан;
- архітектура підтримує кілька одночасних учасників;
- мережеву поведінку можна налаштовувати незалежно від платформи цифрового двійника;
- інтерполяція забезпечує плавний та просторово точний рух аватарів.

Негативні наслідки:

- додається окремий серверний компонент;
- затримка інтерполяції збільшує end-to-end latency;
- мережевий потік сервера зростає зі збільшенням кількості клієнтів;
- екстраполяція непридатна для операцій, де помилка положення може призвести до неправильного інженерного рішення;
- відмова сервера сеансу тимчасово припиняє синхронізацію учасників, хоча фізичний стан цифрового двійника залишається доступним через Eclipse Ditto.
