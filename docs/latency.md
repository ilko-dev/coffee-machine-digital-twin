# Модель наскрізної затримки

## 1. Маршрут телеметрії

Основний маршрут даних від сенсора автоматичної кавомашини
до відображення стану користувачеві:

Sensor / Emulator
→ MQTT Publisher
→ MQTT Broker
→ Telemetry Consumer
→ Data Quality Validation
→ Twin State Manager
→ WebSocket API
→ Web UI

Запис телеметрії до сховища та аналіз аномалій виконуються
паралельно після оновлення стану цифрового двійника.
Тому вони не входять до наскрізної затримки
«датчик — подання».

## 2. Бюджет затримки

| Ділянка | Перетворення | Затримка, мс |
|---|---|---:|
| Sensor → Publisher | формування та серіалізація відліку | 10 |
| Publisher → Broker | JSON, MQTT publish | 20 |
| Broker → Consumer | маршрутизація та доставка MQTT | 40 |
| Consumer → Validation | десеріалізація повідомлення | 10 |
| Validation → Twin State | валідація та оновлення стану | 10 |
| Twin State → WebSocket API | формування push-оновлення | 50 |
| WebSocket API → Web UI | передавання та відображення | 70 |
| **Разом** | | **210** |

Наведені значення є проєктними оцінками, що використовуються
для архітектурного моделювання. Фактичні значення перевірятимуться
експериментально в наступних лабораторних роботах.

## 3. Перевірка NFR-01

NFR-01:

Затримка синхронізації стану від формування телеметрії
до оновлення Twin State Manager повинна бути не більше
250 мс для 95 % оновлень.

До синхронізації входять:

- Sensor → Publisher: 10 мс;
- Publisher → Broker: 20 мс;
- Broker → Consumer: 40 мс;
- Consumer → Validation: 10 мс;
- Validation → Twin State: 10 мс.

Отже:

Lsync = 10 + 20 + 40 + 10 + 10 = 90 мс.

90 мс < 250 мс.

На рівні архітектурної моделі NFR-01 виконується.

## 4. Перевірка NFR-02

NFR-02:

Наскрізна затримка «датчик — подання» повинна бути
не більше 500 мс для 95 % оновлень.

Для поточної архітектури:

Le2e = 210 мс.

210 мс < 500 мс.

На рівні архітектурної моделі NFR-02 виконується.

## 5. Паралельні гілки

Після оновлення Twin State Manager дані також передаються:

- до Telemetry Repository;
- до Anomaly Analyzer.

Ці операції виконуються паралельно і не блокують
передавання актуального стану до Web UI.

Тому їхні затримки не додаються до Le2e.

Якщо в майбутньому інтерфейс буде отримувати поточний стан
через читання зі сховища, запис і читання бази даних стануть
частиною послідовного маршруту та повинні будуть враховуватися.

## 6. Аналіз маршруту

Найбільші затримки поточної конфігурації:

- WebSocket API → Web UI: 70 мс;
- Twin State → WebSocket API: 50 мс;
- MQTT Broker → Telemetry Consumer: 40 мс.

Разом ділянки між Twin State Manager та відображенням
становлять 120 мс із загальних 210 мс.

Тому спосіб оновлення інтерфейсу має суттєвий вплив
на загальну затримку.

## 7. Гіпотеза

### Г-01

Використання push-оновлень через WebSocket замість
періодичного опитування REST API зменшить медіанну
наскрізну затримку «датчик — подання» щонайменше на 30 %.

### Базова конфігурація

Для порівняння розглядається варіант з REST polling.

Припускається, що ділянка від стану цифрового двійника
до відображення при періодичному опитуванні становить:

- Twin State → REST API: 50 мс;
- REST polling → Web UI: 200 мс.

Тоді:

Lbase =
10 + 20 + 40 + 10 + 10 + 50 + 200
= 340 мс.

### Конфігурація з WebSocket

Для WebSocket:

Lws =
10 + 20 + 40 + 10 + 10 + 50 + 70
= 210 мс.

Очікуване зменшення:

(340 - 210) / 340 × 100 % ≈ 38 %.

Отже, архітектурна модель підтримує гіпотезу Г-01.

## 8. План експериментальної перевірки

Гіпотеза буде перевірена на двох конфігураціях:

1. REST polling;
2. WebSocket push.

Умови тесту:

- однакова частота телеметрії;
- однакова кількість сигналів;
- однакове навантаження;
- однакове середовище виконання.

Для кожного телеметричного повідомлення фіксуються:

- timestamp формування на джерелі;
- timestamp відображення в Web UI.

Основна метрика:

- медіана наскрізної затримки.

Додатково:

- p95 затримки;
- максимальна затримка;
- кількість отриманих оновлень.

Гіпотеза вважається підтвердженою, якщо медіанна
наскрізна затримка WebSocket-конфігурації буде
щонайменше на 30 % меншою за REST polling.
